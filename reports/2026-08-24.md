## 요약

- 구버전 Governance 기준에서 시작된 PR #10을 종료하고, Contract v1.7이 적용된
  `main`에서 `codex-sortable-core-v1-7` 브랜치를 새로 생성했다.
- 기존 PR의 최종 기능 상태만 squash 이관했으며, 과거 커밋별 검증 결과는 재사용하지
  않고 v1.7의 라이선스, 보안, 모듈, 브라우저 순서로 다시 검증했다.
- 같은 drop target을 재확인하는 Playwright helper가 불필요하게 영역 밖으로 이동했다가
  재진입해 `insert` 이벤트를 중복 발생시키던 테스트 계약을 수정했다.
- production Playground build 뒤에도 Vite 개발 서버를 사용해 최초 dependency
  optimization reload가 drag 입력을 중단하던 구성을 production preview 서버로
  전환했다.
- PR #12의 CI에서 WebKit이 같은 페이지의 두 번째 drag를 시작할 때 helper의 인위적인
  영역 이탈을 안정적으로 처리하지 못하는 현상을 확인했다. 실제 outside 동작은 DOM
  상태, accepted destination은 placeholder, rejected destination은 transform 좌표로
  완료를 확인하고, `moveBefore`는 목적지로 직접 이동하도록 정리했다. 모든 pointer
  입력은 Core가 배치 처리하는 `requestAnimationFrame` 완료 후 상태를 판정한다.
- Linux WebKit 진단에서 목적지 hit-test는 정확했지만 drag transform이 `0px`에 머문
  것을 확인했다. `pointer-events: none`이 되는 dragging source 대신 안정적인 area
  element에 pointer capture를 설정하도록 Core sensor 경계를 수정했다.

## 실패 분류 및 조치

- 첫 browser 실행의 로컬 포트 `EPERM`은 샌드박스 환경 실패로 분류하고 권한이 허용된
  동일 소스 상태에서 재실행했다.
- 첫 전체 browser 실행은 동일 target 재진입 12건과 재현되지 않은 React resource
  1건으로 192/205였다. helper 수정 후 전체 205/205를 확인했다.
- 첫 Playground 실행은 Vite 개발 서버의 cold optimization reload로 Chromium 5건이
  실패했다. production preview 전환 후 전체 81/81을 확인했다.
- PR #12의 첫 CI는 Core 205/205를 통과했지만 Playground WebKit의 반복 drag 5건이
  단일 영역 이탈 move의 반영을 기다리다 실패해 76/81이었다. 영역 이탈, accepted
  destination, rejected destination의 실제 반영 조건을 각각 polling하고 pointer move를
  재전송하도록 수정했다.
- 후속 CI에서도 Core는 통과했고 같은 Playground 5건만 76/81로 실패했다. Core의 실제
  outside 취소 경로는 통과했으며 실패는 목적지가 이미 정해진 `moveBefore`와 handle
  재정렬의 인위적인 선행 이탈에만 한정됐다. 선행 이탈을 제거하고 목적지의 공개 완료
  신호를 직접 기다리도록 수정했다.
- 세 번째 이후 CI에서도 같은 5건이 76/81로 실패했으며 source placeholder가 유지됐다.
  timeout 진단에서 목적지 좌표는 viewport 내부이고 `elementsFromPoint`는 올바른 area를
  반환했지만 drag transform은 계속 `translate(0px, 0px)`이었다. dragging source 자체에
  둔 pointer capture가 Linux WebKit에서 후속 move를 전달하지 못하는 원인으로 확정하고,
  source/handle 판정과 capture 대상을 분리해 안정적인 area element에 capture하도록
  수정했다. capture 경계 회귀 테스트 2건과 CI 실패군 WebKit 45/45를 확인했다.
- rejected destination의 최초 완료 조건은 CSS transform 문자열 완전 일치였으며,
  WebKit이 0.5px 소스 좌표를 정수로 반올림해 4/4 실패했다. 실제 transform 행렬의 x/y를
  1px 오차로 비교하도록 수정한 뒤 focused 12/12와 전체 browser 205/205를 확인했다.
- stable capture 변경 후 첫 전체 browser는 React resource activation 1건으로 204/205였다.
  같은 테스트를 격리해 10/10 통과한 뒤 전체 browser를 다시 실행해 205/205를 확인했다.
