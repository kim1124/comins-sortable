# 0.1.2 성능 및 메모리 검증

이 문서는 `comins-sortable@0.1.2` 후보의 Playground 기능 동작과 Chrome
리소스 안정화 결과를 기록한다. npm 배포 완료를 의미하지 않는다.

## 검증 범위

- React Playground 24개 예제를 사이드바 순서대로 실행했다.
- 정렬, 목록 간 이동, 복제, Alt 복제, 핸들, 전환 애니메이션,
  다중 선택 이동, Thresholds, Grid, Swap, component host, slot, 중첩
  목록, 빈 대상, 거부 정책, 자동 스크롤, Tree API,
  Custom/Skeleton Placeholder를 실제로 동작시켰다.
- Tree API는 루트의 일반 node를 모두 자식 area로 이동한 뒤 자식 node를
  다시 루트로 꺼내는 왕복 경로까지 실행했다.
- 기존 Playground 게이트는 동일한 24개 경로를 Vanilla, React, Vue,
  Svelte에서 모두 마운트하고 각 어댑터의 기능 계약을 검증한다.
- 측정 항목은 Chrome DevTools Performance Monitor의 JS Heap, DOM Nodes,
  Event Listeners다.

## 수동 Chrome DevTools 절차

1. `npm run dev`로 Playground를 실행한다.
2. `/examples/two-lists/react`를 열고 DevTools의 **Performance Monitor**를
   표시한다.
3. Memory 패널에서 **Collect garbage**를 실행하고 기준값을 기록한다.
4. 24개 예제를 순서대로 열어 각 예제의 핵심 동작과 결과를 확인한다.
   탭 전환만 수행하지 않는다.
5. `two-lists/react`로 돌아와 데이터를 초기화하고 다시 GC를 실행한다.
6. 첫 실행의 절대 증가량만으로 누수를 판정하지 않고, 동일 작업을 한 번
   더 반복해 Heap·DOM·listener의 증가 기울기가 안정화되는지 확인한다.

OpenAI Chrome 플러그인은 페이지 조작에, Computer Use MCP는 실제
DevTools Performance Monitor와 Memory 패널 조작 및 숫자 판독에 사용했다.

## 수동 측정 결과

| 단계 | JS Heap | DOM Nodes | Event Listeners |
| --- | ---: | ---: | ---: |
| 새로고침 및 GC 기준 | 9.0 MB | 242 | 365 |
| 삭제 전 23개 기능 실행 직후 | 22.7 MB | 888 | 629 |
| 동일 화면 복귀 및 GC | 16.7 MB | 872 | 366 |

Event Listeners는 기준 대비 `+1`로 회수됐다. 반면 해당 DevTools 세션의
Heap과 DOM은 완전히 회수되지 않았다. Detached Elements 검사에서 이전
Playground UI 노드가 확인됐으며, DevTools 프로파일과 브라우저 자동화가
관찰한 DOM 참조도 포함될 수 있으므로 이 단일 세션의 절대값만으로 제품
누수를 판정하지 않았다.

이 수동 측정값은 테이블 행·열 예제를 제거하기 전 23개 경로 기준의 비교
기록이다. 현재 24개 경로 기준은 아래 독립 Chromium 자동 게이트로 다시
검증했다.

## 독립 Chromium 대조 측정

확장 프로그램이 없는 Chromium에서 CDP `HeapProfiler.collectGarbage`,
`Performance.getMetrics`, `Memory.getDOMCounters`로 Performance Monitor와
동일 계열의 리소스를 재측정했다.

탭 전환만 11회 수행한 최소 재현은 첫 순환에서 Nodes가 `221 → 261`로
증가했지만 두 번째 순환에서도 `261`을 유지했다. Event Listeners는
`329`로 유지했고, Heap은 `4.61 → 4.72 MB`였다. 이는 첫 순환의 React 및
동적 모듈 워밍업 비용과 선형 누수를 구분하는 대조 근거다.

현재 24개 기능을 실제 실행하는 자동 게이트의 결과는 다음과 같다.

| 단계 | JS Heap | DOM Nodes | Event Listeners | Live DOM |
| --- | ---: | ---: | ---: | ---: |
| 기준 | 3.90 MB | 437 | 333 | 142 |
| 전체 기능 1회 | 6.55 MB | 557 | 377 | 142 |
| 전체 기능 2회 | 6.99 MB | 557 | 377 | 142 |

두 번째 전체 실행에서 DOM Nodes, Event Listeners, Live DOM은 증가하지
않았고 JS Heap 증가는 `0.44 MB`였다. 따라서 반복 실행 기준의 선형 DOM
또는 listener 누수는 재현되지 않았다.

## 자동 게이트

```sh
npm run verify:performance
```

게이트는 다음 조건을 만족해야 한다.

- 두 번째 실행의 document 수와 live DOM 수가 첫 실행과 동일하다.
- Event Listeners 증가는 `5` 이하이다.
- DOM Nodes 증가는 `10` 이하이다.
- JS Heap 증가는 `1 MB` 이하이다.

절대 기준값은 Chrome 버전, DevTools, 개발 모드, 확장 프로그램에 따라
달라질 수 있다. 회귀 판정은 동일 환경에서 워밍업 후 반복 실행의 증가량을
사용한다.

## 기능 검증 중 발견한 결함

두 번째 전체 실행에서 Accept/Reject UI toggle은 이전 `false` 상태를
유지했지만 새 데모 런타임은 `true`로 초기화되는 불일치가 발견됐다.
경로 변경과 데이터 초기화 시 toggle 상태를 기본값으로 동기화하도록
수정했으며, 전용 성능 게이트와 전체 Playground 검증에서 회귀를 확인했다.

Tree API에서 child node를 루트로 다시 이동할 때 순차 area setter의 두 번째
갱신이 이전 parent snapshot의 자식 배열을 재사용하여 `DUPLICATE_ITEM_ID`를
발생시키는 결함도 확인했다. `updateArea`가 기존 node의 현재 descendant를
보존하도록 수정했으며, 네 어댑터의 왕복 회귀 시나리오와 전체 Playground
195개 테스트에서 확인했다.

다중 선택 이동에서는 드래그 시작 위치가 원본 목록 인덱스를, 충돌 계산은
선택 항목을 제외한 목록 인덱스를 사용해 값이 우연히 같을 때 Placeholder가
갱신되지 않는 결함을 확인했다. 시작 위치도 선택 제외 인덱스로 정규화하고
Core 단위 회귀 테스트 및 네 어댑터의 WebKit 시나리오로 확인했다.
